# API Quick Reference

Endpoints with quick examples. For full schema see [OpenAPI](../openapi.json).

- POST /api/tasks/add (TaskCreate) -> { data: TaskDTO }
- GET  /api/tasks/list -> { data: { total, limit, offset, tasks? } }; `tasks` is a `TaskDTO[]` page and is
  omitted when the page is empty (treat missing as `[]`); empty page:
  `{ "data": { "total": 0, "limit": 50, "offset": 0 } }`, populated page:
  `{ "data": { "total": 1, "limit": 50, "offset": 0, "tasks": [ { "id": "QA-1", "title": "Wire contract tests", "status": "Todo", "priority": "Medium", "task_type": "Feature", "created": "2026-09-15T10:00:00+00:00", "modified": "2026-09-15T11:30:00+00:00" } ] } }`
- GET  /api/tasks/get?id=ID[&project=PREFIX][&include_deleted=true] -> { data: TaskDTO }; default reads hide deleted tasks
- POST /api/tasks/update (TaskUpdateRequest) -> { data: TaskDTO }
- POST /api/tasks/delete ({ id, hard?: bool }[?project=PREFIX]) -> { data: { deleted: bool, hard: bool, warnings: string[] } }; soft by default; hard deletion retains attachments and warns about retained attachment references and incoming task relationships
- POST /api/tasks/restore ({ id }[?project=PREFIX]) -> { data: TaskDTO }; restores without changing `modified`
- POST /api/sprints/create (SprintCreateRequest) -> { data: SprintCreateResponse }; configured sprint defaults apply unless `skip_defaults: true` (see `applied_defaults`, omitted when empty)
- POST /api/sprints/update (SprintUpdateRequest) -> { data: SprintUpdateResponse }; sprint must be >= 1 (0 -> 400); omitted fields are unchanged, `null` clears `capacity_points`/`capacity_hours`/`actual_started_at`/`actual_closed_at` while `null` on single-value fields is treated as omitted; 404 for unknown sprint ids
- POST /api/sprints/delete ({ sprint, cleanup_missing? }) -> { data: SprintDeleteResponse }; sprint must be >= 1; 404 for unknown sprint ids; tasks keep their data
- POST /api/tasks/attachments/upload ({ id, filename, content_base64 }) -> { data: { stored_path, attached, task } }; uploads attach typed `attachment` references
- POST /api/tasks/attachments/remove ({ id, stored_path }) -> { data: { task, deleted, still_referenced } }; 400 when the task lacks the managed `attachment` reference (blob untouched)
- POST /api/automation/simulate ({ ticket_id, event, project? }) -> { data: { matched, rule_name, actions, task_before, task_after } }; `event` is one of created, updated, assigned, commented, sprint_changed, job_started, job_completed, job_failed, job_cancelled (case-insensitive legacy aliases accepted); automation scope follows the ticket's project (`project` is ignored); `rule_name`/`task_after` are explicit `null` when no rule matched
- GET  /api/config/show[?project=PREFIX] -> { data: object }
- POST /api/config/set ({ values, global?, project? }) -> { data: { updated: bool } }
- GET  /api/events -> text/event-stream (see SSE Events)

Notes
- List/export support `deletion=active|deleted|all`, default `active`. Ordinary mutations reject deleted tasks until restored. Lifecycle operations preserve `modified` and append their own timestamped history.
- People fields accept `@me`.
- /api/tasks/list accepts additional query keys beyond the documented ones: declared custom field names can be used directly (e.g., `?sprint=W35`). Values support CSV and fuzzy matching (case/sep-insensitive).
- /api/tasks/update validates `status`, `priority`, and `type` against the task's project configuration.
- Validation errors return 400 with INVALID_ARGUMENT.
- Task/sprint domain errors preserve `{ error: { code, message } }`: invalid arguments/identity/safety refusals map to `400 INVALID_ARGUMENT`, missing resources to `404 NOT_FOUND`, and I/O/serialization/index failures to `500 INTERNAL`. Unknown positive sprint IDs, including task-create membership references, return 404; zero/invalid IDs return 400.

## Relationship graph and repair

The user help ([../help/api-quick-reference.md](../help/api-quick-reference.md)) keeps a short summary. Full rules:

- Graph exact typed-ID exceptions include full/padded `REL-2`/`REL-002`, compact `REL2`/`REL002`, and numeric `2`/`002` when unique in the project-scoped strict inventory. Project case is exact; ambiguous numeric/compact matches are not guessed. These identity matches survive `include_isolated=false` and rank before other query matches at the node cap, while still satisfying all non-text filters. Resolution does not use title matches or let other filters manufacture unique numeric identity.
- Graph REST accepts `kinds=dependency,hierarchy` (comma-separated canonical kinds; `kinds=` selects none; omit for all) and strict `include_isolated=true|false`. The client/MCP request fields are `relationship_kinds` and `include_isolated`. Omitted options retain legacy projection. With `include_isolated=false`, isolated matching seeds are removed before budgeting, except an explicit focus, unique exact-ID search, or unresolved identity. Matching and sorting precede pair/component-aware allocation so recent isolates cannot displace linked clusters. Context endpoints may cross project/filter boundaries. `max_nodes` is never exceeded; `truncated` reports eligible omissions, and global integrity diagnostics remain independent of selected kinds. Focus `depth` is undirected BFS hops (0-8), not layout stages; project-wide graphs use all matching seeds with at least one boundary hop.
- Fresh graph/check issues always include opaque `id`. For a per-issue fix, preview repair with `{ "issue_ids": ["<id>"], "apply": false }`, then apply with the same project/IDs and returned revision. The server recomputes diagnostics and refuses unknown, stale, unsafe or out-of-scope IDs; client `repairable` is not authority. Tokens bind full inventory bytes, project and sorted unique selected IDs. Selected repair responses scope `issues` before/after to those IDs and `changed_tasks` to necessary changes only. Alias-only repair substitutes the selected raw spelling without deduplicating; duplicate-only repair keeps the first stored spelling without canonicalizing; missing-mirror-only repair adds only that counterpart without normalizing existing entries. Multiple selected actions are independent of ID order, with selected aliases substituted before selected deduplication. Unselected diagnostic types are not opportunistically repaired. Omitted/empty `issue_ids` preserves batch combined normalization. Repair retains transactional history and post-commit events without starting jobs.
- CLI parity: `task relationships graph --relationship-kind dependency --include-isolated false --filter 'status:todo tag:ui'` (`--filter` takes the web search syntax, the same as the `query` filter key) (repeat `--relationship-kind` to combine kinds; omitted options retain legacy behavior), and `task relationships repair --issue-id <id>` (repeatable; apply with the same IDs and `--apply --expected-revision <preview-token>`).

## List and export query rules

- `/api/tasks/list` and `/api/tasks/export` share one strict query executor: `sort_by` accepts the builtin keys (`priority`, `status`, `effort`, `due-date`, `created`, `modified`, `assignee`, `reporter`, `title`, `type`, `project`, `id`, `tags`, `sprints`, `relevance`) plus `custom:<name>` (alias `field:<name>`); `relevance` orders by how well tasks match `q`, best first with the default `desc` (see [search text](../help/list.md#search-text)); `tags` compares the tag array lexicographically and `sprints` the ascending sprint-id list numerically (empty first ascending); `order` is `asc|desc` (default `desc`); `priority` and `status` sort in their configured order (priorities lowest to highest, statuses in workflow order), other values after them by name; invalid explicit enum values, sprint entries, smart filters, sort/order params, or page params (`limit` must be 1-1000) return `400 INVALID_ARGUMENT` instead of being ignored or clamped. `has` keeps tasks carrying every listed kind: `attachment`, `image`, `link`, `tag` (at least one tag). `recent=Nd|Nw` keeps tasks modified within the last N days or weeks (in `query`, `-recent:30d` keeps the ones not changed for 30 days); `due_within=N` keeps tasks due from today through today + N days; `effort_min`/`effort_max` are inclusive effort bounds (`2h`, `1d`, `3pt`; time and points never compare, tasks without an effort are left out). `assignee=__none__` keeps unassigned tasks. `query` takes filters and search text in the web search-box syntax, exactly as `lotar list` does (e.g. `query=status:todo prio:high has:tag -tag:wip "login redirect"`; a leading minus excludes a filter), and adds to the other parameters; `q` stays plain search text, where `tag:x` limits a word to tags rather than filtering by tag. Explicitly blank `due`/`due_within`/`recent`/`needs`/`has`/`effort_min`/`effort_max` values are errors — omit the parameter instead. The CLI `lotar list` and MCP `task_list` run the same query (see [list](../help/list.md#filters-in-the-query)).
